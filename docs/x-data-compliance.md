# X 开发者条款与数据存留核对

> 草稿。依据是搜索摘要和本仓库代码，不是法律意见。核对时 docs.x.com 被出口策略拦截，协议原文没有读到，第 2 节的条款都是摘要，需以官方原文为准。

## 1. 结论

- 授权长期保存的圈子会把推文摘要、作者用户名和头像地址写入 SQLite，并可能同步到 Git 备份（`lib/circle-payload.ts`、`lib/github-backup.ts`）。
- 摘要显示，官方协议把通过 API 取得的帖子副本、帖子 ID 和个人资料都算作 X Content，禁止再分发；合规文档要求离线副本与平台当前状态保持一致。
- 代码里没有按单条删除长期圈子的入口，也没有与 X 删除状态同步的机制。这是使用官方数据前必须先解决的问题。
- 现有的 Yahoo、FxTwitter 抓取同样包含 X 内容，风险并不因为换到官方 API 就消失。区别是官方 API 有合同约束，违约后果更明确。

## 4. 本项目的数据存留（代码事实）

| 数据 | 存放位置 | 保留规则 | 代码 |
|---|---|---|---|
| 互动摘要（tweetId、作者、被提及者、时间、正文摘要） | `yahoo_circles.circle_data`（JSON） | 正文截断到 180 字符；开启自动清理时，临时圈子 168 小时后删除；授权长期保存的不过期 | `lib/interactions/text.ts:1`、`lib/providers/yahoo.ts:60`、`lib/app-config.ts`（`temporary_retention_hours`） |
| 头像地址、显示名、资料统计 | 同上 | 同上 | `lib/circle-payload.ts:200-222`、`lib/circle-convert.ts:94-108` |
| 长期圈子备份 | Git 仓库中的 gzip JSON | 默认关闭自动备份；提交为非强制更新，历史版本保留 | `lib/github-backup.ts:92`、`:196`、`:232` |
| 头像图片 | 图片代理的 Next 数据缓存与 CDN 缓存 | 7 天 | `app/api/image-proxy/route.ts:8`、`:43` |
| 圈子数据的访问 | `/api/circle/[id]` 与 `/circle/[id]` | 知道圈子 ID 即可读取，没有访问控制 | `middleware.ts`（只保护 `/admin` 与 `/api/admin`） |

删除路径：

- 临时圈子：自动清理或手动清理，只针对 `storage_consent = 0`（`lib/db.ts:224`）。
- 长期圈子：没有单条删除入口。只有管理后台的整表替换导入会先执行 `DELETE FROM yahoo_circles`（`lib/admin-data.ts:353`）。

## 5. 可能冲突的地方（待法务判断）

1. 长期保存的副本与"副本需与平台状态同步"的要求之间，没有对应的机制。
2. 公开圈子页和 OG 图展示推文摘要与头像，是否允许取决于展示要求的具体内容。
3. 头像缓存 7 天，取决于缓存权利是否明确。
4. Git 历史保留旧版本，删除之后仍可从历史中取回，与删除同步的目标冲突。
5. 长期保存的同意由发起生成的用户给出（`storage_consent`），圈子里出现的被提及者没有单独同意。

## 6. 建议（工程层面，本次未改动生产代码）

1. 为长期圈子增加单条删除，并记录删除操作。
2. 设计删除同步：定期检查已存推文是否仍然可见，不可见则删除副本。是否可行取决于官方接口和计费，需要先确认。
3. 减少存留字段：正文只保留必要片段，头像只留在缓存里，不写入数据库。
4. 备份改用私有仓库并加密，或者不把长期数据放进 Git 历史。
5. 记录同意文案的版本，并在生成页说明被提及者的数据会被处理。
